# heatcalc 架构审查与改进清单

核对日期：2026-10-26。依据为当前工作区的 Python、Vue、测试、依赖与接口实现；包含本轮用户确认的压缩机进口管道压降修复。

目标是为公司建立基于 LangChain 的工业快速核算智能体。现阶段已实现工业热源相关的 7 项计算工具，适合继续完善为可复核的核算系统。本文中除明确标为“已完成”的事项外，均为审查意见或待确认方案，不代表代码已经实现。

## 1. 协作与修改约定

1. 一次讨论一个问题，先说明当前行为、业务影响和建议规则。
2. 由用户确认业务逻辑、公式、单位、边界条件及预期结果。
3. 获得用户明确同意编写代码后，再实施对应变更和必要测试。
4. 验证后更新文档与问题状态，再讨论下一项；提出改进意见不等于获得实现授权。

本轮最初仅授权更新文档，随后用户明确授权修复回热器至压缩机压降，并确认“实际进口压力由上游出口减去管道压降推导”。其余问题尚未获得代码修改授权。

## 2. 当前架构与合理之处

```text
Vue 对话 / 参数表
  → FastAPI /api/chat
    → LangChain bind_tools + 最多 5 轮手写调用循环
      ├─ 参数表工具 → 中文字段、分组、单位倍率、部分示例值
      └─ 7 个计算工具
          ├─ 电加热器策略
          ├─ 热泵策略 → CoolProp 循环 COP
          ├─ 熔盐储量公共函数
          └─ 风光制汽计算（目前直接位于 tools.py）
    → 本轮原始结果 / 展示结果 → 模型生成回复
  → 前端内存中的消息列表
```

已有设计值得保留：工业数值由 Python 和物性库计算；大模型负责理解需求、选工具和解释；充热与供汽时长分开；计算值与展示值分开；设备策略与独立储盐函数可复用；多个对话的前端请求归属已有回归测试。

当前依赖包含 LangGraph，但运行流程没有使用图或检查点。手写循环本身可以支撑当前工具数量；是否采用 LangGraph，应由状态保存、中断恢复和流程复杂度决定。现阶段没有证据表明需要先引入多智能体、向量数据库或全面重写框架。

## 4. A01：压缩机进口管道压降（已完成）

位置：[cop.py](../src/heatcalc/cop.py) 的 `calculate_cop`。

原实现收取 `regenerator_to_compressor_pressure_drop`，但未用于任何状态计算。原示例该值为零，因此没有暴露问题；原实现中把它改为 100 kPa，四项返回结果完全不变。

用户已确认并实施的逻辑：

```text
压缩机实际进口压力
  = 回热器低压侧出口压力 − 回热器至压缩机管道压降
```

实际进口压力用于进口焓、进口熵及后续压缩状态计算。若该压力不是大于零的有限数值，在查询物性之前报出明确错误。

验证：原零压降示例 COP 仍为约 1.7403367161，输入电功率仍为约 57460.14497 kW；回热器出口 2700 kPa、管道压降 100 kPa 时，进口物性按 2600 kPa 查询，COP 与电功率随之变化。另已验证不大于零和非有限的推导压力会被拒绝。

兼容边界：原 `compressor_inlet_pressure` 仍是函数和工具的必填兼容字段，实际计算已不采用其独立输入值。移除这项冗余字段会涉及工具 Schema、表单与调用方，归入 A06，待另行确认。

## 5. A02：参数校验未形成统一规则

位置：[tools.py](../src/heatcalc/agent/tools.py)、[cop.py](../src/heatcalc/cop.py)、[strategy.py](../src/heatcalc/strategy.py)、[chat.py](../src/heatcalc/backend/routers/chat.py)。

已确认的表现：

- 电加热和热泵策略检查了部分时长、效率、流量和焓差；风光制汽直接查询 IAPWS95，未复用这套检查。
- 风光工具的说明写明效率必须处于 `(0, 1]`、功率不得为负，但自动生成的工具 Schema 主要检查类型和必填项，没有落实这些范围。
- COP 除 A01 新增的实际进口压力检查外，尚未统一拦截负热功率、超范围效率、负压降和无效状态关系。
- 蒸汽接口检查了正焓差，但尚未显式确认用户给出的“蒸汽”确实处于允许的汽相工况。饱和两相核算需要什么输入也未明确。
- 工具异常会向外抛出，尚未统一转换成字段错误与补参回复。

本次本地调用复现，未调用模型：

| 输入变化 | 当前结果 |
| --- | --- |
| 风光输入功率从 8000 改为 -8000 kW | 返回负电功率和约 -3.31485 t/h 蒸汽流量 |
| 风光转换效率设为 2 | 接受输入，并按额定功率限幅后继续计算 |
| 风光供汽时长设为 0 h | `ZeroDivisionError` |
| 独立 COP 热功率设为 -100000 kW | 返回负循环流量、负电功率和正 COP |
| 独立 COP 电动机效率设为 2 | 接受输入并返回 COP 约 3.55171 |
| 独立 COP 热功率设为 0，机械损失也为 0 | `ZeroDivisionError`；热泵正反算已有停机分支 |

建议先确认：哪些量允许零、哪些必须为正；效率和压降范围；压力采用绝压还是表压；过热蒸汽、饱和蒸汽及两相状态是否支持；无效工况应返回哪些字段提示。零热功率是否代表停机、是否计入待机损失，也需要统一口径。

建议验收：所有入口对同类工况执行相同规则，非法输入在物性调用前或计算有效性检查中被明确拒绝，并能指出需修正的字段。单纯依靠模型补问不能替代后端校验。

## 6. A03：COP 模型的工程有效性仍需确认

位置：[cop.py](../src/heatcalc/cop.py) 的回热器、换热器和系统功率计算；[pump_heater.py](../src/heatcalc/pump_heater.py)。

已确认的实现：回热器两侧出口温度分别按同一个端差指定，再独立查焓；未通过两侧能量平衡求解其中一个出口状态，也未对两侧焓差的差异做检查。

按 README 空气示例，低压侧每千克介质吸热约 **31.58889 kJ/kg**，高压侧放热约 **32.41182 kJ/kg**；以低压侧吸热为基准，相差约 **2.60512%**。这说明当前算法没有保证该回热器的焓差平衡。它是否属于原模型允许的简化、是否需要热损失项，以及误差容限，应先确认，不能直接自行改公式。

此外，COP 使用熔盐最低温度确定放热器出口，未接收熔盐最高温度并校核最高温度能否达到；余热侧也未提供可用余热量或热源流量。因此“热泵满足给定热功率”的数值尚不等于热源和换热过程实际可行。

待确认：循环与换热模型的适用介质和范围、回热器出口的求解方式、管道压降时采用什么热力学假设、机械损失及膨胀功回收边界、最高供热温度与余热容量限制、允许的能量平衡误差。

储盐也需明确口径：当前按全部充热量折算盐量；若公司目标是边充边供场景中的最小储热库存，需要时间轴与库存差计算，不能直接把现有结果当作动态容量优化结果。

## 7. A04：会话文字与核算任务状态混在一起

位置：[useConversations.ts](../frontend/src/composables/useConversations.ts)、[chat.py](../src/heatcalc/backend/routers/chat.py)、[agent_core.py](../src/heatcalc/agent/agent_core.py)。

前端下一轮只发送 `role` 和 `content`。后端本轮得到的 `updated_messages` 没有保存或返回，其中的工具参数、原始结果和调用记录随请求结束丢失。表单提交的参数 JSON 也仅进入当轮模型上下文，下一轮主要依赖中文摘要和模型回复重新理解。

具体影响：用户先计算购电成本，再说“用刚才的结果算盐量”，模型可能从已经舍入的文字重建数值；同一对话比较不同方案时，无法由程序确定参数属于哪一个方案、是否已被覆盖、哪些是用户确认值。

建议先确认一个最小核算记录：计算任务 ID、目标工具、已确认输入及单位、输入来源、缺项、原始结果、模型或公式版本、时间、与上次计算的关联。大模型读取和解释记录，程序负责保存与执行。是否使用 LangGraph 检查点是后续实现选择。

建议验收：连续修改一个参数时，其他确认参数不漂移；跨轮串联工具使用保存的原始值；刷新或重开任务后的恢复行为有明确约定。

## 8. A05：单位与结果展示应有确定的契约

位置：[parameter_specs.py](../src/heatcalc/agent/parameter_specs.py)、[formatting.py](../src/heatcalc/agent/formatting.py)、[agent_core.py](../src/heatcalc/agent/agent_core.py)。

已有表单单位倍率和结果格式化函数，但自然语言输入中的 MW→kW、t/h→kg/s 仍主要由模型换算；表单字段使用的单位又不完全相同。当前 API 只返回回复文字和参数表，工具原始值、标准展示值没有作为独立计算结果返回前端。

影响：提示词可以要求最终数值遵循 `display_result`，但程序没有保证回复中的单位和数字确实一致，也无法单独审查模型是否遗漏或改写关键结果。

建议确认统一的参数定义，包含类型、内部单位、显示单位、范围、来源及确认状态；计算接口返回结构化结果，由前端确定格式化关键数字，大模型负责说明。单位规范应明确 MPa/kPa、MWt/MWe、MWht/MWhe、kg/s/t/h 的边界。

## 9. A06：工具边界与参数定义存在耦合

位置：[strategy.py](../src/heatcalc/strategy.py)、[tools.py](../src/heatcalc/agent/tools.py)、[parameter_specs.py](../src/heatcalc/agent/parameter_specs.py)。

- 仅计算电加热电费或蒸汽流量，也必须输入熔盐比热、最高温度和最低温度。这些值在该电费链路中不参与数值计算；本次将比热设为负值、温差设为负值，电费结果仍完全相同。额外必填项拖慢补参，还会让用户误以为已经做了储盐校核。
- 热泵电费工具中，熔盐最低温度参与 COP，但比热与最高温度未进入该成本链路；需要按实际依赖区分。
- A01 修复后，压缩机原进口压力也属于兼容但不再控制计算的输入。
- COP 参数在函数签名、多个工具签名、字典组装和表单说明中重复维护，新增字段容易遗漏。
- 风光制汽的业务计算留在 Agent 工具层，复用和测试的边界与其他工具不一致。
- 参数表从签名派生，但全部标为必填并返回完整表；“只补缺项”与已知值合并目前主要是模型规则。

建议先确认每项核算真正需要哪些参数，再统一参数模型和工具注册定义；储盐物性仅由涉及储盐的计算要求。兼容字段的移除要同时考虑现有调用者，不在本轮自动清理。

## 10. A07：Agent 和后端运行边界不完整

位置：[agent_core.py](../src/heatcalc/agent/agent_core.py)、[chat.py](../src/heatcalc/backend/routers/chat.py)。

- `async def` 接口直接调用同步 `chat()`，其中同步访问模型和计算；等待模型时会阻塞同一工作进程的事件循环。前端允许多个对话并发，并不代表服务端已经具备对应处理能力。
- 工具校验错误、物性异常和模型异常没有统一处理。前端只收到通用失败提示，难以区分缺参、工况不成立和服务故障。
- 最多 5 轮之后直接返回最后一次 `response.content`，若仍是工具调用，没有明确的“达到上限”回复和恢复策略；未知工具分支也没有形成完整的工具错误消息。
- 没有应用层明确的请求时限、历史长度限制、任务级取消和运行状态。浏览器取消请求不保证终止已经开始的模型调用。

建议确认：哪些错误应交回用户修正，哪些允许自动重试，哪些应停止；每项任务最长多久，用户如何取消，执行到什么状态必须返回可理解的结果。再据此选择同步线程、异步调用或后台任务方案。

## 11. A08：测试覆盖需要对应真实核算流程

位置：[tests](../tests)、[frontend/tests](../frontend/tests)。

现有测试对策略正反算、时长关系、格式化和前端对话隔离已有价值。但没有针对 `agent_core.chat` 和 HTTP 对话接口的自动化测试；风光示例主要打印结果，没有断言数值或非法输入行为。COP 本轮已增加压降回归，其他物理约束仍需单独设计验收。

建议先由用户确认少量代表场景：缺参→补表→计算；修改单参数重算；跨轮调用储盐；同一对话比较两方案；单位混用；不成立工况；模型或工具失败。用受控模型响应验证执行流程，真实模型另做小规模业务验收，不能用“测试通过数量”代替核算有效性。

## 12. A09：界面展示和参数来源需要准确表达

位置：[App.vue](../frontend/src/App.vue)、[MessageBubble.vue](../frontend/src/components/MessageBubble.vue)、[parameter_specs.py](../src/heatcalc/agent/parameter_specs.py)。

“模型服务已连接”是固定文本，`/api/health` 也不检查模型；“方案”“档案”按钮尚无操作。单独 COP 表单预填部分 Excel 示例，其中包含零损失值，提交后作为输入使用；其他热泵成本工具没有同一套默认值。

待确认：示例是否只用于演示，还是允许用作公司推荐工况；采用示例时是否需要整组确认和来源标记；旧表单能否重新提交并覆盖当前参数。循环介质下拉目前只有 air，而 Python 函数支持更多介质，也需按公司实际支持范围统一。

Markdown 当前通过 `marked` 和 `v-html` 展示，没有专门 HTML 净化；多人使用前应处理这条实际渲染边界。

## 13. A10：公司使用范围决定后续平台能力

当前没有账户、权限和后端持久化；没有可导出的核算记录、公式与版本追踪、项目或方案管理。模型名在两个入口分别写死，前端接口地址固定；早期终端入口与网页 Agent 的规则不同，`uv run heatcalc` 当前只打印问候语。依赖中的 LangGraph、langchainhub 尚未进入实际流程。

建议先明确第一阶段的使用者、核算类型、需要保留哪些输入与结论、哪些数据允许发送到所配模型服务，再决定账户、存储、报告导出和部署方式。无需在这个阶段先把项目扩展成通用工业平台。
